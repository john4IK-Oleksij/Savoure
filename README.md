## 🏛️ Еталон чистого та безпечного коду (Developer & Agent Benchmark)

Цей проєкт створений як **архітектурний зразок (golden standard)** для розробників та AI-агентів. Будь-які модифікації або нові модулі мають відповідати наступним 5 золотим правилам:

1. **Ізоляція секретів (Zero Secrets in Git):**
   * Жодних захардкоджених паролів, API-ключів, персональних даних чи секретних ключів у репозиторії.
   * Конфігурація читається суворо з середовища (`.env` або Railway Variables). На продакшні заборонено використовувати тестовий `SECRET_KEY`.
2. **Максимальна безпека кук (Cookie Hardening):**
   * Сесійні куки передаються виключно з прапорцем `HttpOnly` (захист від викрадення через XSS) та `Secure` (передача тільки через шифрований HTTPS).
   * Захист від міжсайтових атак через `SameSite=Lax`.
3. **Імунітет проти ін'єкцій (XSS / SQLi / CSRF):**
   * Усі запити до БД — виключно через параметризовані запити Django ORM.
   * Усі форми захищені `{% csrf_token %}`.
   * Усі динамічні HTML-фрагменти екрануються через `format_html()` — сирий `mark_safe()` на клієнтських даних суворо заборонений.
4. **Прогресивне покращення та легкість клієнта (Zero-Weight Architecture):**
   * Жодних важких сторонніх бібліотек на зразок jQuery чи Axios там, де достатньо нативного сучасного JavaScript ES6+ (`fetch()`, CSS `:has()`).
   * Будь-яка форма працює як через плавний фоновий запит без перезавантаження сторінки, так і через стандартний серверний fallback при вимкненому JS.
5. **Передбачуваність та обробка помилок (Defensive Error Handling):**
   * Форматування дат використовує безпечні ASCII-специфікатори, що виключає збої `UnicodeEncodeError` системної локалі на різних ОС.
   * Захист цілісності бази даних від збоїв при спробі повторної підписки або дублювання унікальних полів.

## 🗺️ Roadmap & Ітерації реалізації проєкту

Нижче наведено дорожню карту виконаних інженерних ітерацій з контрольними мітками якості та безпеки:

### Ітерація 1: Інфраструктура, Безпека секретів та Айдентика бренду
- [x] **1.1. Контейнеризація:** Налаштовано легкий `Dockerfile` на базі `python:3.12-slim` з динамічним портом Railway `$PORT`.
- [x] **1.2. Статичні файли:** Інтегровано WhiteNoise з кешуванням та стисненням `CompressedStaticFilesStorage`.
- [x] **1.3. Айдентика бренду:** Повна відмова від сторонніх шрифтових іконок на користь векторного SVG-контуру Ейфелевої вежі (`templates/_eiffel_icon.html`).
> **Security Check:** Секрети ізольовані в середовищі. База даних перемикається автоматично через `dj_database_url`.

### Ітерація 2: Двигун бронювання та Інтерактивна схема зали (12 столиків)
- [x] **2.1. Доменна модель:** Створено модель `Reservation` з підтримкою зон зали (Вікно, Центр, Камін).
- [x] **2.2. Інтерактивна карта:** Розроблено векторну схему зали з 12 столиками (рояль, сцена, бар, панорамні вікна).
- [x] **2.3. Живий вибір:** Клік по вільному столику прив'язує його до форми; зайняті столи автоматично блокуються.
> **Security Check:** Валідація ліміту гостей (2–8 осіб на стіл), CSRF-захист на формі бронювання.

### Ітерація 3: Побажання гостей та Кастомізація Backstage
- [x] **3.1. Візуалізація приводів:** Інтегровано кольорові бейджі свят (*Wedding*, *Birthday*, *Romance*) у таблицю адмінки.
- [x] **3.2. Форматування часу й дат:** Європейський формат `ДД.ММ.РРРР` та `ГГ:ХХ` замість довгих текстових описів.
- [x] **3.3. Компактність стовпців:** Номер столика з його зоною (наприклад, `№1 (Вікно)`).
> **Security Check:** Текст побажань екранується через `format_html` — ризик XSS виключено.

### Ітерація 4: Оперативний план зали для Менеджера та Захист від випадковостей
- [x] **4.1. Обов'язковий фокус:** Призначення столика дозволяється лише після явного вибору рядка бронювання.
- [x] **4.2. Фільтр за датою:** План зали відображає зайнятість суворо на день обраного візиту.
- [x] **4.3. Кнопка скасування:** Додано скидання чернеткових призначень без натискання "Назад" у браузері.
> **Security Check:** Виключено людський фактор перезапису чужого бронювання при випадковому кліку на стіл.

### Ітерація 5: Рольова модель (RBAC) та Захист системних груп

> **Security Check:** Усунуто потенційну 500 помилку Django `GroupAdmin`, забезпечено цілісність прав доступу персоналу.

### Ітерація 6: Преміальна система сповіщень Savoure (Toast System)

### Ітерація 8: Керування меню, Стоп-лист та Зручний перехід до сайту
- [x] **8.1. Відкриття сайту в новій вкладці:** Посилання "ДИВИТИСЯ САЙТ" у шапці відкриває вітрину з `target="_blank"` та `rel="noopener noreferrer"`.

### Ітерація 9: Харденінг продакшну та Повний аудит безпеки

## 🛠️ Швидкий старт для розробника

### 1. Клонування та налаштування оточення
```bash
git clone https://github.com/john4IK-Oleksij/Savoure.git
cd Savoure
uv venv
uv pip install -r requirements.txt
```

### 2. Створення локального файлу змінних середовища (`.env`)
```env
DEBUG=True
SECRET_KEY=local-dev-secret-key-savoure-2026
ALLOWED_HOSTS=localhost,127.0.0.1,testserver
DATABASE_URL=sqlite:///db.sqlite3
```

### 3. Запуск міграцій та локального сервера
```bash
python manage.py migrate
python manage.py runserver
```
Сайт буде доступний за адресою: `http://127.0.0.1:8000/`  
Панель керування: `http://127.0.0.1:8000/backstage/`

### 4. Запуск аудиту коду та тестів безпеки
```bash
# Перевірка стилю та відсутності помилок лінтера:
uv run ruff check .

# Перевірка цілісності системи Django:
uv run python manage.py check

# Офіційний аудит безпеки перед деплоєм:
uv run python manage.py check --deploy
```
